# Delayed birth materialization — private alternative for design disproof

2026-09-06. Baseline4592a41. Proposal ONLY: explicitly revisits ControllerV3's
stage-then-undo mechanism. Does not replace that reviewed direction without a new
reviewed contract. No source implementation, production caller, cleanup, semantic
fact identity fix, lifecycle adoption or live authorization from this document.

## Question and evidence motivating it

The actual resolver creates declared entities before resolveFacts. It also creates
both endpoint stubs before rejecting an assertion whose other endpoint cannot
resolve. A declaration or stub with no accepted assertion can therefore commit as
a hollow. ControllerV3 plans exact raw undo of unsupported births, and its later
identity-mutation review correctly requires complete cross-birth alias ownership
closure: undoing an earlier A claim must not erase supported B's later claim, and
unchanged al bytes can become a new defect when their owner is removed.

Could keeping NEW identities and their alias proposals entirely in a transaction-
local overlay until accepted assertion dependencies are settled avoid the need for
ordinary unsupported-birth raw undo? The existing registration ledger, original
observations, B-style in-memory episode votes, and immutable result concepts still
apply. This is a concrete alternative to test, not permission to discard existing
independent counterexamples, all-writer controls, or historical fact safeguards.

## Proposed fixed boundary

One Store-owned admission scope owns exact parsed revision, baseline identity/fact
inventories, registration handles, resolution overlay, proposed metadata, original
ordinal/side mappings, explicit dependency records and the final actual writers.
The production API takes episode/parsed inputs, never accepted-support flags,
caller-cleanup lists, raw virtual after-images or a replaceable finalizer.

Use the reviewed serialized graph boundary for the whole snapshot/plan/write/commit.
Existing normal pending queue writes remain outside that graph lock. All overlay
operations are private Store-owned methods reachable through an opaque context,
not an exported fake Store with arbitrary Set/Delete or caller-populated owners.
No new concurrency/raw writer guarantee is claimed by the overlay.

Register each baseline-absent candidate from its exact original observation BEFORE
its first metadata/alias proposal. Baseline current OR historical FA references
defer it as already designed; consumed/retired/invalid selectors refuse. A repeated
mention stays bound to its first handle and full additional original observations,
even though no en row exists. Existing identities validate current generation or
reviewed legacy anchor through EVERY normal/exact/artifact/fact-only lookup path.

New candidate en metadata and proposed aliases live only in memory during planning.
No en/al/ig/iga/att mutation or entity-created event occurs merely for declaration,
endpoint discovery, alias vote, or a rejected assertion. New candidates use B's one
distinct current-episode vote, never old att capacity or the presence of a temporary
en as a reason to switch to legacy evidence. Preserve every original proposal in
structured observations/outcomes, including unsupported conflicting metadata.

## Overlay lookup is an explicit dependency, not ownership inference

Preserve established/exact identity and artifact/value vetoes, explicit aliases,
cross-type resistance, canonical homonym refusal and natural-slug identity checks.
No owner chosen by fact count, name similarity, sentence heuristic, or fixpoint
frequency. Registration alone does not grant alias authority. Every candidate alias
proposal still passes the existing reviewed admission rules adapted to B evidence;
the overlay records exact existing-owner conflicts and actual proposal ordering.

When resolution uses an already admitted provisional spelling or canonical candidate
name, record the exact candidate handle/proposal dependency for that original
occurrence. No speculative Supersedes-only name creates a candidate. An accepted
primary assertion using candidate A thereby requires A as an endpoint; that is a
planned dependency, not yet a factual-support certificate. Dependency-only hints
do not turn their named slugs into new entities.

An unsupported candidate can have blocked another proposal during planning. Do NOT
silently reroute/reassign ownership after removing that candidate from the materialized
set. Recompute nothing by an unreviewed winner rule. Either the rejected proposal
remains a recorded ordinary alias rejection with unaffected useful assertions, or
the precise affected assertion dependency component is deferred as unresolved.
This utility/ordering choice needs disproof and a frozen policy before code. It
must not leave a retained entity listing a spelling that was never admitted.

For A-proposes-k, A-releases-k, B-proposes-k, retain B only if its final proposal has
independent permission against the BASELINE index/identity controls and every
retained listing. An intermediate unsupported A cannot grant B a transfer from a
real old owner. No raw restoration occurs: any eventual al write is a new approved
final action from its actual baseline. Existing defects remain explicit unchanged
relationships, never implicit permission or new generation authority.

## Plan assertions before either current resolver mutation phase

Resolve every original fact into a typed primary/dependency description retaining
original ordinal and original-to-final side mappings before mutation. Cover empty
normalized relation, two values, unresolved primary endpoint, and whole Supersedes
dependencies. Unknown relation fallback is not an invalid-relation skip.

Preflight primary fact addresses, exact eligible supersession targets, exclusive
invalidation targets, and any historical/backdate relocations BEFORE Phase A merges
confidence/provenance or Phase B invalidations. Assertions plus hints are atomic
dependency units; ambiguous/unrecognized/deferred targets defer their connected
mutations, while genuinely unrelated units proceed. No typed deferral gets coerced
to an empty slug or value just to permit a different write.

The fact planner must preserve existing two-phase semantics: restatements merge
against the episode's pre-invalidation current state, all eligible hints apply even
for Phase-A-merged primaries, and later exclusive assertions preserve the declared
ordering contract. A single unchanged snapshot query is insufficient to model
within-episode writes; use owned staged fact-plan state and exact ordered effects.
This planner does not get to discard facts, timestamp-nudge collisions, or approve
the currently unresolved current assertion-identity/recovery bug. Any unproved
fact collision/component must refuse/defer visibly under a separate reviewed rule.

## Delayed writes and final proof

From the accepted typed assertion plan, derive the exact new candidate set used
as source or entity destination by at least one accepted PRIMARY fact. Hint-only
dependencies never add to that set. This is Store-computed plan state, not a caller's
support list. Plan-selected candidates are staged immediately before their required
fact effects; supported existing identities receive their separately approved
metadata updates. Only final approved new alias listings/index claims are staged.

Execute exact planned fact mutations through the owned actual ledger, preserving
old assertion content/time/confidence/provenance and dependency atomicity. Any
staging/conflict error rolls back the entire transaction. Final raw inventories
must match the full actual write ledger and preflighted accepted mutation semantics.
Every staged new identity must have zero baseline raw FA references and at least
one FINAL current/historical raw reference produced by this scope's approved plan.
Every plan-used new endpoint must have its exact registered stable identity.

If a supposedly supported candidate has no actual final assertion, treat it as a
planner/accounting violation and refuse atomically; do not invent support or use
raw undo as a silent fallback. For a correct accepted plan referencing a new slug,
baseline-zero references mean its first actual assertion cannot merely disappear
into a preexisting old fact. Later same-episode invalidation still leaves historical
support. This reasoning needs tests for matching/no-op/relocation/order interactions,
not an assertion that counts alone authorize facts.

Only after actual proof materialize B generation evidence for this supported set.
Unsupported candidates never had en/al effects to undo and never get ig/iga. Their
complete proposed metadata stays in descriptive no-assertion outcomes, including
a synthetic materialization snapshot if needed for inspection; do not label it
an entity that was actually stored. The outcome contract permits an opaque object,
but user-visible terminology must distinguish proposal from actual materialization.
Persist EP-proven observations and complete episode result/head in the same commit.

Final global relationship checks still apply to ALL changed retained en/al keys,
listing occurrences, raw owners including unlisted claims, natural-slug routes and
lifecycle controls. Existing identities and facts are never provisional cleanup
targets. Eliminating unsupported raw writes does not authorize alias theft, old
metadata loss, dropped repo refs, baseline defect changes, or lifecycle bypasses.

## Required disproof and decision

Determine whether this concretely reduces the raw undo requirement WITHOUT changing
useful identity resolution or disguising failures as deferrals. Inspect actual
resolveEntity/AdmitAlias/ensureEntitySlug/resolveFacts and their dependencies, not
just this narrative. Especially challenge aliases of not-yet-materialized candidates,
declarations that are values/artifacts, repeated conflicting types, canonical-vs-
alias precedence, A/B proposals and baseline stolen/unlisted claims, two-phase fact
semantics, old dangling/history-only endpoints, hint-only deferrals and atomic
partial utility. State exact required overlay API/producer coverage and whether
a smaller independent planning primitive can establish it safely.

If a counterexample requires actual unsupported en/al mutation to preserve required
semantics, show it. If the alternative merely moves the same ownership ambiguity
into an unreviewed plan, say so and pin the smallest necessary policy. Do not infer
approval to weaken the original EmptySlugSkipped expectation silently: the intended
contract change remains no unsupported node plus retained input/unrelated facts.

This is a fresh architectural alternative, not an implementation pass or decision
to activate it. All-writer generation/legacy consumption, fixed support policy,
immutable results/Force, complete assertion identity, cleanup/recall and two full
goal grading rounds remain mandatory. Root is sole builder and live writer.
