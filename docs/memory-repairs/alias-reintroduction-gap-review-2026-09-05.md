## Why the code permits it

- `internal/memory/store/unalias.go:242` backs up and executes the reviewed batch transaction. Its mutations at lines 268–291 update entity alias lists and set/delete `al:` routing keys only. Exact entity/fact/index postconditions correctly enforce the repair's immediate result, but no durable owner/name prohibition is written.
- `internal/memory/store/store.go:1222` (`DropAliasRehome`) likewise removes the normalized aliases/index or rehomes the index, without recording the rejected pair. `store/pending.go:246` retains positive per-owner/per-normalized-name attestations; neither drop implementation invalidates their authority.
- `internal/memory/resolve/aliases.go:237` checks aliases, retired spellings and lexical/current-owner rules but has no reviewed pair-denial query. At lines 396–401, two attestations can admit any otherwise eligible unowned candidate. `admitAliases` at line 406 feeds it into normal resolution; `resolve.go:291–327` unions admitted aliases and writes the entity.
- `store.go:396` (`PutEntity`) preflights retired names/slugs, existing identity compatibility and competing current index owners. A removed alias absent from current `prevNorms` and absent from `al:` is a new unclaimed alias, so it passes and is indexed. Stale writes also bypass resolver lexical admission. `AtomicWrite` at line 235 uses the same implementation and transaction-visible state; atomicity does not supply missing rejection policy.
- This stale read/write shape is real in metadata-only code: `internal/daemon/memory_methods.go:469–473` gets an entity, changes its description, then PutEntity; `memory_queue.go:727–741` similarly updates repo refs. Each individual write is atomic, but its older payload can span an intervening reviewed removal. This is a mechanism/race risk, not a claim that this interleaving was observed live.
- Raw lower-level `ClaimAlias` (`store.go:1185`) checks global retirement, then directly writes `al:`. Explicit `DropAliasRehome` also writes the target directly. Reviewed alias repair and entity merge use direct transaction writes rather than PutEntity. `store/merge.go:144–212` changes entities/facts/claims directly; merge `DropAliases` currently supplies removal disposition, not persistent owner denial. Protecting only AdmitAlias or only PutEntity would leave other paths inconsistent.

## Minimal safe invariant proposed — not implemented

For each **explicitly reviewed** normalized spelling N and forbidden identity O, store a durable, fingerprinted decision that N must not be listed as O's name/alias or indexed to O by any ordinary write, admission, stale metadata write, or low-level claim operation. Absence of an index is not revocation of this decision. Any number of positive attestations cannot override it. A denial for `(ChildScribe, Envoyer)` is neither a global retired-value/name marker nor an inferred assignment to Forge, a future Envoyer tool, or anyone else.

- Persist the normalized pair and its review provenance/reason atomically with the alias removal, including rehome removals. Keep the decision across reopen, backup/restore and subsequent metadata updates. Fingerprint it in previews and recheck it in the apply transaction. Normalization-equivalent literal variants share one decision.
- Consult it before admission shortcuts and attestations. Enforce the same invariant in PutEntity's transaction for all new name/alias claims, including stale and atomic callers; a typed conflict must refuse the whole write without partial metadata, fact, marker or index changes. Existing legacy-conflict tolerance must not bypass a reviewed negative decision. Include low-level ClaimAlias and direct repair writers in the same check.
- Explicit rehome should forbid the source pair while allowing only its independently reviewed target; refuse a target already denied for that spelling unless an explicit reviewed supersession of the denial is part of that operation. Never infer an owner just to keep a key occupied.
- A merge must explicitly account for relevant denied pairs on survivor and losers. It cannot make a denial disappear merely by changing the owner slug, nor import a denied spelling from the other identity. Safest initial behavior is refuse unresolved denial/name conflicts and require reviewed dispositions; any later decision transfer or supersession belongs in the exact merge manifest and its postconditions, not an automatic global blacklist.
- Existing live49 decisions need a separate explicitly reviewed, drift-checked negative-evidence manifest against a fresh backup. Do not infer denials from every historically absent alias or replay the old drop manifest blindly. Preserve every original fact, episode and positive attestation; negative evidence can take precedence without deleting history.
- Proof tests should cover same-normalized variants, arbitrary repeated/new/reused episode attestations, own-name/slug shortcuts, stale PutEntity, transaction-visible staged writes, metadata-only callers, direct ClaimAlias, rehome target conflicts, merge survivor/loser dispositions, exact backup/restore durability, atomic rollback and permanent queue conflict parking. Include genuine unrelated Envoyer-tool and other-owner alias positives. No lexical wordlist expansion or global value retirement is needed.
